# AGENTS.md — Sports Emotion Storefront

Adobe Commerce Storefront on **Edge Delivery Services (EDS)** for Sports Emotion, built on
`aem-boilerplate-commerce` with a custom layered architecture. Act as an expert Adobe Commerce
Solutions Architect for **storefront/frontend work only**. Follow this file exactly.

## Scope

**In scope:** EDS blocks, drop-in customization (PDP, PLP, cart, checkout, auth, account),
content modeling, CSS/JS frontend work, performance (Lighthouse 100 target), and GraphQL/REST
consumption from the storefront.

**Out of scope — stop and redirect:** backend integrations and App Builder extensions.
Customer/product/stock/order sync and external webhooks → **Integration Starter Kit**.
Payment/shipping/tax webhooks and Admin UI SDK → **Checkout Starter Kit**.
Clarify the Commerce target (PaaS or SaaS/ACCS/ACO) before generating backend-dependent code.

## Key Technologies

Edge Delivery Services (docs: https://www.aem.live/ — restrict searches with `site:www.aem.live`),
Adobe Commerce Storefront drop-ins (docs: https://experienceleague.adobe.com/developer/commerce/storefront/llms.txt),
vanilla JS (ES6+, no transpiling, no build step), modern CSS (no Tailwind or CSS frameworks —
see docs/adr/0005), HTML decorated client-side from aem.live markup, Node.js tooling.

## Architecture

Layered, with imports allowed **downwards only** (enforced by ESLint):
`blocks → ui → dropins → domain → core → vendor`. Communicate upwards only via events
(`scripts/core/events.js`). Full rationale: `docs/ARQUITECTURA-FRONTEND.md` and `docs/adr/`.

```
blocks/                  # Thin adapters over dropin containers (one folder per block:
                         #   <name>.js + <name>.css + README.md; complex blocks add sections/)
scripts/
  aem.js                 # VENDOR — never modify (CI-protected)
  __dropins__/           # VENDOR — generated by postinstall, never edit by hand
  scripts.js             # EDS page orchestrator (eager/lazy/delayed)
  core/                  # Own platform: config, graphql, events (catalog), routes,
                         #   storage (key catalog), i18n, auth, consent, error, lifecycle
  domain/                # Business logic: analytics (ACDL), product, seo
  dropins/               # registry.js (ensureCapability) + declarative initializers
  ui/                    # guards, layout (data-ref), modal, dropin-block, slots/
  commerce.js            # DEPRECATED facade (re-exports only — never add code here)
  initializers/          # DEPRECATED shims for unmigrated blocks
styles/styles.css        # Design tokens + critical CSS; Sports Emotion theme overrides
                         #   live ONLY in the marked block at the end of the file
skills/                  # Agent skills (project-manager, researcher, block-developer,
                         #   dropin-developer, content-modeler, tester)
docs/                    # Architecture doc + ADRs · test/ — Vitest unit tests
```

### Rules for new code

- Declare commerce dependencies via `ensureCapability('<name>')` from `scripts/dropins/registry.js`
  (or `mountDropinBlock` from `scripts/ui/dropin-block.js`) — never side-effect imports of
  `scripts/initializers/*`.
- No magic strings: routes from `core/routes.js`, storage keys from `core/storage.js`,
  event names from `core/events.js`.
- No user-visible text hardcoded in JS: use placeholders (`core/i18n.js#fetchPlaceholders`)
  with the current text as fallback. No literal colors/sizes in CSS: use design tokens.
- JSDoc-typed exports; use `logger` from `core/logger.js` instead of raw `console`.
- Layout scaffolds use `scripts/ui/layout.js` (`data-ref` attributes, single source of truth);
  create dynamic elements with `document.createElement()`. Never use VNode/Preact elements.

## Workflow & Skills

For every **new task**: load the `project-manager` skill first and run its Task Complexity
Assessment before implementing (simple task → offer direct vs guided; complex → phased workflow).

**Research is mandatory before implementing** — use the `researcher` skill, whose primary tool is
the `commerce-extensibility:search-commerce-docs` MCP (maxResults ≥ 10, iterate up to 10 searches,
follow doc URLs). **Never assume slot names, event payloads, container props or API functions** —
verify in docs, TypeScript definitions (`scripts/__dropins__/**/*.d.ts`) or the codebase.

Skill handoff: `block-developer` (create/modify blocks), `dropin-developer` (slots, containers,
dropin events), `content-modeler` (authoring structures), `tester` (browser verification),
`researcher` (any information lookup).

## Blocks & Content Modeling

- **Check existing blocks first** (`/blocks` and block-collection) before creating one — never
  skip the reusability check (see block-developer skill).
- Blocks must be self-contained, responsive and accessible; scope every CSS selector to the block;
  avoid `{blockname}-container`/`-wrapper` class names (used by sections).
- The authored content structure is the author↔developer contract: design it first, code
  defensively (authors may omit/add fields), and keep changes backwards compatible.
- Prefer **content blocks** (directly authored); use config blocks sparingly and only for config.
  Authors are non-technical: if they struggle with the structure, it is wrong.

## Drop-ins

- Customize only through supported surfaces: initializer config, **slots**, design tokens and
  `build.mjs` (`overrideGQLOperations`) — never fork dropin internals or their CSS.
- Prefer container props over CSS workarounds. In slot callbacks use context methods
  (`replaceWith`, `appendChild`, `replaceHTML`) — never return elements.

## Styling

Mobile first; `min-width` media queries at 600px/900px/1200px only. All theming through the
tokens in `styles/styles.css`; brand changes go exclusively in the "SPORTS EMOTION — THEME
OVERRIDES" block. Below-the-fold global CSS goes to `lazy-styles.css`.

## Testing & Performance

- Unit: Vitest (`test/unit/`) for core/domain/ui and checkout sections — keep green (`npm test`).
- Always verify changes in a real browser (dev server or preview), including responsive
  viewports and keyboard/ARIA accessibility. Never assume URL patterns — check `href`s or ask.
- Target Lighthouse 100 (https://www.aem.live/developer/keeping-it-100): images optimized,
  non-critical work in lazy/delayed phases, minimal eager JS.

## Deployment

Branches deploy automatically via AEM Code Sync:
preview `https://<branch>--<repo>--<owner>.aem.page/`, production `https://main--<repo>--<owner>.aem.live/`.
PRs must include a preview URL demonstrating the change and pass lint + PSI checks.
Run a PageSpeed Insights check against the feature preview URL before requesting review.

## Contributing

- Commit messages MUST be in English, following Conventional Commits
  (`feat: …`, `fix: …`, `refactor: …`, `test: …`).
- Every touched block needs an up-to-date `README.md` (enforced by pre-commit hook); component
  model changes (`_*.json`) regenerate `component-*.json` automatically on commit.
- Never commit secrets; everything ships as public client-side code. `config.json` is local-only
  (gitignored); the real one comes from the AEM config service.
- Consent/GDPR: analytics is gated by `scripts/core/consent.js` (CMP pending — see
  `scripts/core/consent-providers/README.md` and docs/adr/0004).
